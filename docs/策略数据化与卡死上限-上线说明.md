# 策略数据化（任务 3）与三条卡死上限（任务 6）上线说明

版本：v1.8 · 2026-10-27
对应说明书：《飞脑改进执行说明书-给电脑端》v1.1 的任务 3 与任务 6

## 一、这次改了什么（一句话）

把散落在代码里的行为策略搬进 `spec.json` 顶层段，让它跟业务配置共用同一套版本、对比、回滚；
再给 ReAct 循环加三条中断条件，让"重复调用、卡在慢接口、连续吐坏格式"这三种真实事故能自己停下来。

两件事都不增加任何新能力，只是让它从"能跑"变成"敢交给业务"。

## 二、任务 3：策略归入 spec.json 顶层段

### 2.1 为什么不新建 policy.json

说明书 v1.0 让新建 `policy.json`，v1.1 已改正，这里记下判断依据：飞构（v1.7）已经把 `spec.json`
做成了配置真源——有历史、能语义 diff、能原子回滚、留审计。再引一份 `policy.json` 就是第二个真值源，
而飞构管不到它：回滚时 spec 回去了、policy 还停在坏版本，系统"配置半新半旧"，是最难排查的一种状态。

所以策略作为 `spec.json` 顶层段，一次回滚全部生效。

### 2.2 新增的三个顶层段

```json
"modes": {
  "default": "default",
  "definitions": {
    "plan":    {"read": "allow", "write": "suspend", "dangerous": "deny"},
    "default": {"read": "allow", "write": "confirm", "dangerous": "confirm"},
    "auto":    {"read": "allow", "write": "confirm", "dangerous": "confirm"},
    "yolo":    {"read": "allow", "write": "allow",   "dangerous": "allow"}
  },
  "yolo_allowed_roles": []
},
"limits": {
  "max_steps": 20,
  "max_wall_clock_seconds": 600,
  "same_call_repeat_limit": 3,
  "malformed_json_limit": 2
},
"egress": {
  "enabled": false,
  "allow_schemes": ["http", "https"],
  "allow_domains": [],
  "allow_ports": [80, 443],
  "trust_upstream_origins": true,
  "deny_private_networks": true,
  "deny_metadata_endpoints": true,
  "max_response_bytes": 5242880,
  "request_timeout_seconds": 15
}
```

`modes` 与 `egress` 本次只落配置与读取路径：模式闸门（任务 2）与出站管控（任务 1'）在后续任务里打开，
`egress.enabled=false` 时行为与改造前完全一致（透传）。

### 2.3 `tool_policies` 扩展而不是新增 `tools` 段

说明书 v1.1 示例里另起了 `tools` 段，但飞脑已有 `tool_policies`（含 roles / max_calls_per_run / requires_confirm）。
再加一个 `tools` 就是同一件事写两处。做法是把两个字段并进现有结构：

```json
"ingest_doc": {"class": "write", "max_calls_per_run": 1, "roles": ["admin","ops"],
               "requires_confirm": true, "timeout_seconds": 30}
```

- `class` 决定模式闸门怎么放行（read / write / dangerous），缺省时按 `requires_confirm` 反推
- `timeout_seconds` 决定单次调用等多久，`_upstream_get` 的超时不再是代码里的魔数

### 2.4 坏配置拒绝启动（安全项）

新增 `SpecError` + `validate_spec()`，在模块导入阶段执行：

- 读不到 / 不是合法 JSON → 报文件路径与解析错误
- 缺必需段（brand / users / upstreams / pilots / approval / tool_policies）→ 报**缺哪个段**
- `upstreams.*.base` 不是 http(s) / `tool_policies.*.class` 取值非法 / 模式缺某类动作 → 指名报错
- 校验通过后 `apply_spec_defaults()` 补可选段默认值——**只补内存，不写磁盘**，
  飞构的快照永远是文件原文（否则「启动快照」会和 git 里的文件对不上）

服务起不来就是起不来，不会静默用默认值跑起来。

### 2.5 只读排障接口

`GET /api/ai/policy`（登录即可，不要求 admin）：返回生效的 modes / limits / egress / approval / tools，
外加 `spec.file` 与 `spec.sha`。**不含任何口令、上游账号、上游地址**——只回 `upstreams` 的 label。

### 2.7 已知边界与取舍

| 项 | 决定 | 原因 |
| --- | --- | --- |
| `approval.ttl_minutes` 不改名 `ttl_seconds` | 保留原键 | 改名要动代码、测试和线上待审批单的过期判定，收益为零；语义不变 |
| `approvers` 暂不做分组（`write_to_prod`） | 不做 | 现在没有"写生产"类工具，加了也是空配置；真需要时用 `tool_policies.*.approver_group` 接 |
| `egress` 本次只落配置 | 不启用 | 出站管控是任务 1'，本次不碰 `urlopen` 路径，`enabled=false` 完全透传 |
| `limits.max_steps` 与 `pilots.react_max_steps` | 两者共存，取小 | 前者是硬上限，后者是常规步数；`min(pilots, limits)` 就是实际步数 |

## 三、任务 6：三条卡死上限

### 3.1 三条中断条件

在 `react_run` 循环里只增加判断，不改循环结构：

| 条件 | 依据 | 触发后的行为 |
| --- | --- | --- |
| 墙钟超时 | `limits.max_wall_clock_seconds`（默认 600s） | 中止，报告已跑多久、上限多少、任务号可续看 |
| 三连相同调用 | `limits.same_call_repeat_limit`（默认 3） | 第 3 次**执行前**中止，报告"连续 N 次调用 X 且参数相同" |
| 连续畸形输出 | `limits.malformed_json_limit`（默认 2） | 降级为纯文本回答，把模型原话交给用户，不算中断 |

### 3.2 一个实现时定下来的关键位置

重复计数放在**角色校验与预算校验之后**，只统计"真的要执行"的调用。

第一版放在了 JSON 解析之后、权限之前，结果三条老用例立刻红了：viewer 越权调用 `query_system`
被拒 6 次，第 3 次就被判成"卡死"并中止——把正常的拒绝路径误判成了事故。

同理 `test_budget_denial` 也暴露了边界：search_docs 预算 3 次，如果模型第 4、5、6 次用**完全相同**的参数
继续要，现在的行为是在第 3 次（执行前）就中止，而不是走到预算拒绝。这是期望行为改变——
"同一动作反复重试"本来就该先被卡死上限拦住。该用例已改成每次换查询词，让它专心测预算，
重复调用场景由 `tests/test_limits.py` 专门覆盖。

### 3.3 abort 的语义

不抛异常给用户。做三件事：

1. `task_steps` 落一条 `kind='aborted'`（含原因与现场：工具、参数、已跑秒数）
2. `tasks.status = 'aborted'`
3. `evidence` 落一条含 `{"aborted": reason}` 的 trace，`audit` 记一条 `react_abort`

返回的是人话，例如：

> 连续 3 次调用 search_docs 且参数完全相同，已停止。可能是参数不对或数据不存在——要不要换个查法？

### 3.4 验收记录（`tests/test_limits.py`，4 例）

```
test_repeated_identical_call_aborts   第 3 次执行前中止；实际执行 2 次；任务 aborted；证据含 aborted
test_wall_clock_abort                 0.05s 上限 + 0.12s 慢桩 → 第二轮中止，报文含"超过…上限"
test_malformed_json_degrades_to_text  坏格式连出 2 次 → 降级纯文本回答，任务 done，无工具执行
test_normal_run_not_affected          正常任务仍 done，不误伤
```
