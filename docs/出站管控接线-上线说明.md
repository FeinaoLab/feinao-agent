# 出站管控接线（任务 1'）上线说明

> 日期：2026-10-28
> 范围：`backend/ai.py`（新增出站闸门与唯一出口）、`backend/engine.py`（策略接口补自检）、`backend/spec.json`（`egress.enabled` 打开）、`tests/test_egress.py`（新增 14 例）
> 前情：`docs/策略数据化与卡死上限-上线说明.md` 任务 3 只把 `egress` 段落了配置，代码里没有强制点。本文补上那一步。

---

## 一、为什么必须做这一步

改造前的事实是：`spec.json` 里有一整套出站策略（协议白名单、域名白名单、端口白名单、禁私网、禁元数据端点、响应体上限），
`GET /api/ai/policy` 也如实返回它——**但代码里没有任何一处调用它**。

这种状态的危害比"没有策略"更大：看配置的人以为门是关着的，实际三处 `urlopen` 全都直连。
一次 SSRF 就能把 `http://169.254.169.254/` 拿去换云主机临时凭据，而策略文件里明明写着 `deny_metadata_endpoints: true`。

所以原则只有一句：**策略登记了就必须有强制点，否则等于没策略。**

---

## 二、做法：判断在代码，取值在配置，出口只有一个

### 2.1 三道口子收成一个

改造前全库有三处直接 `urllib.request.urlopen`：

| 位置 | 用途 |
| --- | --- |
| `_call_openai` | 调大模型供应商 |
| `_upstream_login` | 飞系上游登录取 token |
| `_upstream_get` | 飞系上游取数 |

现在统一走 `egress_open(req, timeout, purpose, user)`：先过策略、再限时、最后用 `read_capped()` 限量读回。
绕开它直接 `urlopen` 就是 bug——这是"唯一出口"这条约束的全部内容，靠代码评审和这份文档维持，不靠自觉。

### 2.2 判定顺序（`check_egress`）

```
enabled=false → 全部放行（一个字节都不多拦）
  ↓
协议在 allow_schemes 吗              否 → 拒
主机名是云元数据端点吗               是 → 拒（白名单里写了也拒）
是 spec 里声明的上游/供应商 origin 吗 是 → 放（trust_upstream_origins）
端口在 allow_ports 吗                否 → 拒
allow_domains 非空时主机匹配吗        否 → 拒（支持 example.com 与 *.example.com，按后缀匹配）
deny_private_networks 时解析到私网吗  是 → 拒
  ↓
放行
```

几个刻意的取舍：

- **元数据端点排在可信 origin 之前**。哪怕有人把 `169.254.169.254` 写进白名单或上游地址，也拒。SSRF 的红线不该由配置决定。
- **`allow_domains` 空 = 不限域名**。老配置不写白名单不该突然全断；要收紧就显式写白名单。
- **`trust_upstream_origins` 默认开**。飞系上游大量是 `127.0.0.1:8050` 这类本机回环，`deny_private_networks` 会把它们一起误杀。
  可信的来源是"配置里写下的地址"，不是代码里的硬编码例外——所以换成 `FEINAO_UPSTREAM_KMS=...` 环境变量覆盖时，
  覆盖后的 origin 同样可信（否则演示/联调一改地址就全断）。
- **解析失败按拒处理**。域名解析不出来时放行没有意义（连不上），但明确拒绝能让日志说清是哪一步卡的。

### 2.3 限时与限量

- 超时取 `min(调用方想要的值, egress.request_timeout_seconds)`——策略是天花板，不是建议值。
- 响应体最多读 `max_response_bytes + 1` 字节，多一个字节立刻判定超限。**先读后截是错的**：那等于把大包整个读进内存再丢。
  默认 5MB，对 JSON 接口足够，对"误把文件当接口"足够早地刹住。

### 2.4 拒绝必须留痕

被拒的请求写一条审计（`tool='egress_denied'`，含脱敏后的 URL、purpose、理由），
`GET /api/audit` 里看得见。**URL 记进日志前先剥掉 query 与 userinfo**——query 里可能带令牌。

同理，`_upstream_login` 里遇到 `EgressDenied` 直接向上抛，不再进 `except Exception` 的兜底：
出站被政策拒绝不是"登录失败"，混进"上游登录失败（api/login→…）"里会把排障的人带去查密码。

### 2.5 排障：让策略自己回答问题

`GET /api/ai/policy?egress_test=1` 返回 `egress_selftest`，用当前生效策略跑四条代表性判定
（公开 HTTPS / 元数据端点 / 本机上游 / `file://`），直接给"拦谁、放谁、为什么"。
排障时不用读代码猜逻辑，也不用真去连一次。

### 2.6 同一批补的洞：实体名拼 URL 的路径注入

`upstream_rows()` 把模型给的 `entity` 直接拼进 `api/{entity}?limit=..`。`../../admin/delete` 这类值
指向的还是同一个域名——**egress 按域名判定，天然管不到同源不同路径**，这属于另一类洞。

现在加形状校验：`^[A-Za-z0-9_-]{1,40}$`，不匹配直接拒绝；`limit` 夹到 1–200，`q` 截 200 字符后再 quote。
不指望上游去挡，路径形状在入口就定死。

## 三、配置变更

```json
"egress": { "enabled": true, ... }
```

`backend/spec.json` 与 `feinao-test/spec.test.json` 都已打开。打开始终是**部署决策**：
旧部署升级后若要保守起见，把 `enabled` 改回 `false` 即恢复改造前行为（透传），本次代码不依赖它必须是 true。

打开后实测（演示上游 8099）：

```
egress enabled: True
upstream_rows('bi','sources') → 3 行（spec 声明的 127.0.0.1:8099 可信，正常放行）
check_egress('http://10.0.0.5/x')            → 拒：目标是内网/保留地址 10.0.0.5
check_egress('http://169.254.169.254/...')   → 拒：目标是云元数据端点（SSRF 红线）
```

## 四、测试（`tests/test_egress.py`，14 例）

| 用例 | 守的是什么 |
| --- | --- |
| `test_disabled_passes_everything` | 开关关闭时连元数据地址都放行——没开就不许有行为变化 |
| `test_metadata_endpoint_denied_even_if_whitelisted` | 白名单写了元数据地址也拒 |
| `test_scheme_and_port_rules` | `file://` 与越界端口 |
| `test_domain_whitelist_suffix_match` | 后缀匹配：收 `a.example.com`，不收 `evil-example.com` |
| `test_private_network_denied` / `..._relaxed_by_config` | 私网默认拒、可配置放开 |
| `test_spec_upstream_origin_is_trusted` / `test_trust_can_be_turned_off` | 本机上游不被误杀；信任可关 |
| `test_egress_open_denies_and_audits` | 拒绝落审计，且抛的是 `EgressDenied` 而不是笼统的 URLError |
| `test_egress_open_clamps_timeout` | 超时被策略夹住 |
| `test_read_capped_limits_body` | 响应体上限，且关闭时透传 |
| `test_selftest_is_readable` | 自检结论可读、有理由 |
| `test_entity_path_injection_blocked` | `../../admin/delete` 这类实体名在入口就被拦 |
| `test_safe_url_strips_secrets` | 审计里的 URL 不带 query 令牌与 userinfo |

同时改了 `tests/test_policy.py` 的一处硬断言：原来写死"策略接口里 `egress.enabled` 必须是 False"，
现在改成"接口值必须等于配置文件里的值"——接口要反映配置，而不是反映某个历史常量。

全套回归：**104 passed**（其中 `test_egress` 14 例；接线前 90 例）。

## 五、仍然存在的三个缺口（别以为接线就安全了）

| 缺口 | 说明 | 建议 |
| --- | --- | --- |
| DNS 重绑定 | 判定时解析一次、连接时又解析一次，中间被换 IP 就能绕过私网检查 | 生产环境把校验过的 IP 固定下来直连（需自定义连接器，标准库要绕）；或靠出口防火墙兜底 |
| 本地 stdio MCP | `npx`/`docker` 起的 MCP server 自己发起连接，飞脑的 `urlopen` 管不到 | **直接禁掉**，只允许远程 HTTP 型 MCP（与《飞脑MCP网关选型建议》的推荐一致） |
| 明文 HTTP | egress 只管去哪，不管内容被看 | 上公网必须配 TLS，签名只解决防重放不解决机密性 |

一句话：接线的意义是把"策略自说自话"变成"请求真的被拦"，剩下的三个缺口都要靠部署方式补，不能靠这份代码。
