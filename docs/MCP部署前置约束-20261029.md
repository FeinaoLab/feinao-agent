# 飞脑 · MCP 部署前置约束（stdio / TLS / DNS 重绑定）

> 日期：2026-10-29 ｜ 背景：《出站管控接线-上线说明》与知识库 565 第七章留下的三条「代码补不了、只能靠部署方式解决」的缺口
> 性质：**部署方案约束**——接 MCP 前逐条核对，任何一条不满足就不上生产流量

## 0. react-03 抖动的处理决定（附带记录）

`bench/tasks.json` react-03（查 KMS 评审中文章）在双跑中偶发失败：模型偶尔选 `search_docs`
（本地知识库）而非 `query_system`（KMS 上游）。**决定：保留严格判据，不放宽。**

理由：
- `search_docs` 查的是入库种子文档，没有「评审中」状态字段，选它答不对题——判据失败是真实信号
- 放宽 `tool_any` 会把「选错工具也能过」写进基线，掩盖回归
- 抖动属模型行为，观测口径：双跑 `repeats>=2` 时按「至少一轮通过」记录，但报告需标注抖动次数

## 1. stdio 型 MCP：一律禁用，或强制代理收口

**风险**：egress 强制点只在飞脑进程内的 `egress_open`（socket 层之下的 urllib 路径）。
`npx`/`docker` 起的 stdio MCP server 是独立子进程，自带网络栈，**飞脑完全看不到它的出站**——
等于给每个 server 发了一张免检出站通行证。

**约束（二选一，写进部署文档，不接受口头豁免）**：
1. `spec.json` 不登记任何 stdio 型 MCP；只用远程 HTTP/SSE 型（流量过 `egress_open` + 审批链）
2. 若业务确需 stdio：部署时给子进程注入 `HTTP_PROXY/HTTPS_PROXY` 指向本机强制代理（代理上再做白名单），
   或用独立网络命名空间（netns/container network）收口；两条都没条件做 = 不装

## 2. 携带凭据的链路必须 TLS

**风险**：明文 HTTP 下，签名鉴权只防重放不防窃听。MCP server 若携带 GitHub token、
数据库凭据等，中间链路可见即等于泄露。

**约束**：
- MCP 端点一律 `https://`（egress `allow_schemes` 对 MCP 流量收窄为仅 https 可作双保险）
- 本地 stdio 不走网络不受此条约束，但属于第 1 条管辖
- 飞脑自身对外（nginx /nao/）也应尽快上 TLS，属独立待办

## 3. DNS 重绑定：判定与连接各解析一次

**风险**：`check_egress` 判定时解析域名→校验 IP，`urlopen` 连接时再次解析——
两次解析间攻击者可换答案（TOCTOU），把「公网域名」换成 `169.254.169.254` 或私网地址。

**约束（按优先级）**：
1. 首选：在 `check_egress` 通过后，把解析结果传给连接层 pin 住（代码改造，属 egress 增强，
   已在 egress 文档「后续增强」登记）
2. 部署缓解：出网经代理（代理侧固定解析）；服务器 resolv.conf 不用不可信 DNS
3. `allow_domains` 已收紧为三家模型供应商域名（2026-10-29），攻击面已大幅缩小——
   重绑定要成立还需攻击者控制其中一家域名的解析，现实风险低但非零

## 4. 上 MCP 前的核对清单

| # | 项 | 核对方式 |
| --- | --- | --- |
| 1 | 无 stdio 型 MCP，或已代理收口 | 部署评审签字项 |
| 2 | MCP 端点全 https | `spec` 审查 |
| 3 | `egress.allow_domains` 覆盖 MCP 域名（非空、逐条列出） | `GET /api/ai/policy` |
| 4 | 每个新 MCP 工具进 `tool_policies`（roles/max_calls/requires_confirm） | `spec` 审查 |
| 5 | 密钥不进 spec.json（环境变量注入） | `git grep` 扫描 |
| 6 | 域名白名单变更走飞构版本化（有快照可回滚） | `/api/harness` |
