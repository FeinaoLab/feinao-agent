# 本地测试环境与端口体检（feinao-test / 8081）

> 版本：v2.1 · 对应提交见仓库历史
> 一句话：验收跑在副本上，生产配置一个字节都不碰；连不上服务器时先分清是「没开」还是「被切」。

## 1. 为什么要有这层东西

之前的验收有两种坏的跑法：

- 直接对着 `backend/spec.json` 和 `backend/feinao.db` 跑。跑一次，生产配置多一条修订记录、库里多几篇测试文档；
  改坏一次，就得靠记忆还原。
- 用环境变量临时指到别处，但没人记得指了没指。同一台机器上两个人跑，互相踩。

所以把「测试环境」做成一个**有名字、有目录、有护栏**的东西，而不是一串要背的环境变量。

飞脑本来就有三个开关（`backend/ai.py:16`、`ai.py:125`、`engine.py:561`）：

| 开关 | 作用 | 测试环境的值 |
| --- | --- | --- |
| `FEINAO_SPEC` | 配置从哪读 | `feinao-test/spec.test.json` |
| `FEINAO_DB` | 库写在哪 | `feinao-test/feinao-test.db` |
| `FEINAO_PORT` | 起在哪个端口 | `8081` |

这层东西只是把这三个开关固定下来，外加一道**过不去的检查**。

## 2. 目录

```
feinao-test/
├── spec.test.json     测试配置（与生产同构，只改地址/端口/文案/口令）
├── feinao-test.db     脱敏库副本（由 tools/testenv.py --prep 生成，不入库）
├── DB-INFO.json       这份副本的来源、脱敏命中次数、行数、sha256
└── README.md          三行说明（给不读文档的人）
tools/testenv.py       体检 / 生成副本 / 起服 / 冒烟
```

`spec.test.json` 是入库的（它本身脱敏）；`*.db` 与 `DB-INFO.json` 不入库——副本永远是本地生成的。

## 3. 四条命令

```bash
python tools/testenv.py --preflight        # 体检：端口什么状态、配置归谁、依赖齐不齐
python tools/testenv.py --prep             # 生成脱敏库副本（没有源库时用假上游种子造一份）
python tools/testenv.py --prep --from ~/prod.db   # 有源库时：复制 + 脱敏 + 重算指纹
python tools/testenv.py --serve            # 8081 起服（横幅会写明配置、数据、模型）
python tools/testenv.py --check            # 对 8081 跑冒烟：health/登录/检索/ReAct/策略/基准
```

`--check` 的实测输出：

```

  ✓ health     status=200 飞脑AI Agent网关（本地测试 8081）

  ✓ ask+引用    2 条来源

  ✓ policy     模式 default
  ✓ bench      15 个任务
```

## 4. 护栏（`--serve` 先过这一关，过不了直接退出）

| 拦什么 | 为什么 |
| --- | --- |
| `FEINAO_SPEC` 不在 `feinao-test/` 里 | 不是「名字像生产才拦」，是「不在测试目录里就拦」——改名换路径都绕不过 |
| 指向 `backend/spec.json` | 那是唯一真值源。写脏了，飞构页的历史和 sha 全乱 |
| 指向 `backend/feinao.db` | 生产库只在服务器上，但本地万一有副本，也不该拿来当测试库 |
| 端口不是 8081（且不在 8080–8099） | 8081 是团队约定；跳到 8060 就撞上真服务 |
| `FEINAO_DEMO=0` | 真上游 = 真数据。验证逻辑不需要真数据，需要**可预期的**数据 |
| shell 里配着真模型 Key | 见下条 |

最后一条是这次真踩到的：本机 shell 里带着 `FEINAO_QWEN_KEY`（做别的事用的），测试一跑就走了真模型。
后果不是花钱那么简单——同一条用例昨天过、今天不过，你分不清是代码变了还是模型抽风。
所以 `--serve` 默认把三个 provider 的 Key 清成空串（只在本进程内生效，不动 `.env`、不动配置），
`--check` 会断言 `provider == "mock"`。

要真模型就显式 `--real-llm`，让它出现在命令历史里。

## 5. 同构检查：测试配置不许偷偷变松

本地验收唯一的合法性来自「和线上是同一套策略」。如果为了跑通把 `tool_policies` 的预算调大、
把 `modes` 调松，那验收通过什么也证明不了。

`tests/test_local_env.py` 把两份 spec 拍平成键路径逐键比对，只允许这些键不同：

- `brand.name / full / tagline / port`
- `upstreams.{kms,bi,cc}.{base, demo_base, label, user, pass}`
- `demo.upstream_port`
- `approval.name`、`memory.name`（带「测试」二字的标题）

其余任何一处分叉都会红。写这条时它立刻抓到了我自己加的 `approval.name`——说明它管用。

## 6. 脱敏：按「所有表的文本列」遍历，不列清单

列清单一定会漏，尤其是以后加的新表。所以 `scrub_db()` 直接读 `sqlite_master` 拿全部表、
`PRAGMA table_info` 拿全部文本列，整库过一遍：

| 类型 | 替换为 |
| --- | --- |
| 手机号 | `138****0000` |
| 邮箱 | `user@example.com` |
| 身份证（18 位） | `110101********0000` |
| IPv4（保留 127.0.0.1 / 0.0.0.0） | `203.0.113.1` |
| `sk-` / `ak-` / `ghp-` 开头的密钥 | `***REDACTED***` |
| 腾讯云 `AKID...` | `AKID***REDACTED***` |

两处细节：

1. `harness_rev.sha` 是内容哈希。脱敏改了 `content` 就必须重算 sha，否则飞构页会判定版本被篡改；
   同时在备注里追加「（脱敏副本）」，让人看得出这条不是原始版本。
2. `dev` 库里的 `docs_fts*` 是 FTS5 的影子表，跳过——它由 `docs` 表同步，改了反而会坏。

## 7. 端口体检：80 通、22 不通，不是一回事

`--preflight` 不只报「通/不通」，它区分四种状态，因为这四种指向四种完全不同的原因：

| 状态 | 含义 | 该做什么 |
| --- | --- | --- |
| `open` | TCP 通、应用层有响应 | 正常 |
| `rst` | **TCP 握得上，数据一发出去就被 RST** | 中间设备按协议特征切断 |
| `timeout` | SYN 没有回应 | 端口没开，或防火墙丢包 |
| `refused` | 对端明确回 RST（连接阶段） | 端口没有监听 |

实测（`python tools/testenv.py --preflight`）：

```
端口体检 → <your-host>
  80    open            37ms  HTTP/1.1 200
  8081  open            41ms  HTTP/1.1 404 Not Found
  22    rst             29ms  TCP 握手成功，应用层数据一发出去就被 RST
  8060  timeout       6008ms  SYN 无回应：端口没开或被防火墙丢包
```

结论：

- **80 通**：HTTP 明文，出口设备放行。部署、中继、API 都走这条路可行。
- **22 是 `rst`，不是 `timeout`**：TCP 三次握手能成（中间设备替服务器代答了 SYN），
  但 SSH banner 一到应用层就被切断。这是 DPI 按协议特征封 SSH 的指纹——**跟密码、密钥、账号都无关**，
  换用户、换密钥、改 `sshd_config` 都不会有用。
- **切手机热点能解**：换的是出口，DPI 不在了，问题自然消失。这是最快的验证方式，也证明了「不是服务器坏了」。
- **长期解法**：不跟 DPI 斗。部署走 80/443 上的 HTTP 中继（现有部署链就是这么干的：零依赖中继 + 命令下发），
  SSH 只作为「人在能直连的网络里」时的备用通道。
- **8060 是 `timeout`**：飞脑生产端口没对公网开放，对外只经 nginx。这是对的，不要为了图方便去开。

一句话记法：**`timeout` 是人家没开门，`rst` 是门开了但有人不让进。** 前者改配置，后者换出口。

7. 端到端：8088 起服 → health 是测试配置 → 登录 → ReAct 走 mock 且工具真调到 → 生产 spec 指纹未变 → 测试库被写入

第 7 条特意用 8088 而不是 8081：测的是「机制」，不是那个数字；本地正开着 8081 时也能跑。

## 9. 回退

- 停测试环境：`Ctrl-C`（或结束 `--serve` 的进程）。它自检生产 spec 指纹，退出时会打印「未被触碰」。
- 删掉测试环境的一切：`rm -rf feinao-test/feinao-test.db feinao-test/DB-INFO.json`，再 `--prep` 重建。
- 生产配置从没被这个工具写过——`--serve` 只在内存里换配置，落盘的只有测试目录里的副本。

## 10. 已知边界

- 测试环境的「同构」覆盖配置，不覆盖数据。真实数据的分布（脏数据、超长字段、空值）只有生产有，
  所以本地全绿不等于线上没问题——它保证的是「策略没被写坏」，不是「数据没问题」。
- 脱敏是正则，不是分类器。它能挡住手机号/邮箱/IP/密钥这类有固定形状的东西，
  挡不住「自由文本里提到的人名和项目名」。要把生产库拿出去，还得人工过一遍。
- `--preflight` 的端口结论依赖你**当前所在的网络**。在办公网看到 `rst`、在热点看到 `open`，
  是同一台服务器的两种事实，不是自相矛盾。
