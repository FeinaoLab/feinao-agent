## 一、这次改了什么（一句话）

给双跑的结果补上"人话结论"：不再输出一个分数，而是说清**同一批任务两次执行的差别在哪里**，
并给一句能逐条复核的判断——可以上线 / 先别上线 / 加样本再判 / 任务集没覆盖。

实跑示例（`tool_policies.search_docs.max_calls_per_run` 从 3 改成 0，四个 ReAct/RAG 任务）：

```
结论：先别上线：1 个任务稳定变坏（react-01），新的失败原因是「没有执行预期动作 search_docs（实际：无）」
建议：先别上线
  · 有效性：通过率 1 → 0.75。0 个任务稳定变好、1 个稳定变坏、0 个只差一次判不了、3 个逐条一致
  · 代价基本没动（token、步数都在 ±15% 内）
  · 过程：被策略拒 1 个任务上升（0 → 1）
  · 证据：覆盖 1 → 1
  · 按能力：ReAct 1→0.67
注意：这轮走的是 mock 上游（没有真实模型调用）：只说明链路与策略生效，不能当模型能力结论
注意：只跑了 4 个任务：宏平均容易被单个任务带偏
```

## 二、为什么"不打分"是对的

开放任务的输出没有唯一答案，任何单一分数都是把不确定性藏进一个数字里：
87 分意味着什么？比 84 分好在哪里？换一批任务还是 87 分吗？这些问题都答不出来，
但看数字的人会当真。**这不是我们想要的说服力。**

能站住的只有一件事：同一批任务、同一个判据、两次执行，差在哪。
这也是 Harness² 里 Propose–Probe–Compose 的核心——没有 ground truth 的时候，
比较是唯一可判定的动作。

飞脑比它多一样东西：**evidence 是代码写的，不是模型自述的**。
所以我们的"通过"由任务自带的 `expect` 判定（`bench.judge` 纯函数），不是让另一个模型来夸。

## 三、判稳规则（这一层的全部智力）

### 3.1 单任务：只差一次，不算数

`_task_verdict` 对每个任务给出五种结论之一：

| 结论 | 条件 | 含义 |
| --- | --- | --- |
| `better` | 通过次数 +≥2，或两侧均"全中 vs 全失" | 稳定变好 |
| `worse` | 通过次数 −≥2，或两侧均"全失 vs 全中" | 稳定变坏 |
| `unclear` | 差 1 次，或每格只跑了 1 次 | 判不了，必须加样本 |
| `same` | 通过次数相同 | 没变（可能失败原因变了，那就写进 `new_fails`） |
| `new`/`gone` | 只在一侧出现 | 不参与结论（见 3.3） |

之所以不肯把"3/3 → 2/3"写成变坏：模型本来就会偶发不一样，
一个任务的 1/3 波动在 15 个任务的宏平均里正好是 0.02，看起来像"轻微下跌"，
实际什么都没有。**把噪声写成结论，比不给结论更糟。**

### 3.2 指标：只用已有的五个事实，各带阈值

| 指标 | 口径 | 显著阈值 | 为什么不这么算就会骗人 |
| --- | --- | --- | --- |
| 通过率 | 绝对差 | 0.005 | 唯一的硬指标：任务到底做完没有 |
| 证据覆盖 | 绝对差 | 0.05 | 回答有来源，还是模型自己编的 |
| 单任务步数 | 相对变化 | ±10% | 同样通过，多绕两步就是变贵 |
| token | 相对变化 | ±15% | 无 token 上报时用字符数代理（P0-2 已有） |
| 被拒 / 出错 / 重复动作 / 人工介入 | **按任务数** | ≥0.5 次 | 宏平均会把"1 个任务被拦 5 次"摊成 0.05，看起来像没发生 |

后四个指标本轮新增两个字段：`bench_run.errors`（执行出错或降级的动作数）、
`bench_run.dups`（同动作同参数被执行了不止一次的次数）。
这两个数字以前就躺在 `task_steps` 里，只是从没进过汇总——而"打转"和"报错"
恰恰是**通过率没变、实际已经变差**的两种典型形态。

### 3.3 任务集不同：只比交集

跨轮对照（作业 A 的候选 vs 作业 B 的候选）时，两次跑的任务集可能不一样。
宏平均的分母都不是同一批任务，直接比就是错的。所以先取交集，
只比两边都跑过的任务，并把缺的列在 `scope.only_a` / `scope.only_b` 里，
同时在 `caveats` 里明说。没有交集就直接报"比不了"。

## 四、六种结论形态

| tone | 触发条件 | 建议动作 | 说明 |
| --- | --- | --- | --- |
| `worse` | 有稳定变坏、没有稳定变好 | 先别上线 | 结论行点名任务 + 新的失败原因 |
| `mixed` | 既有变好又有变坏 | 加样本再判 | 净额经常是 0，本质是"换了个坑" |
| `better` | 有稳定变好、没有变坏 | 可以上线 / 能上线，先算成本 | token 涨超 50% 时把价写进结论行 |
| `wash` | 全没变，但更贵（步数/token） | 别上 | "只买到成本" |
| `cheaper` | 全没变，但更省 | 可以上（省成本） | "白捡的省" |
| `flat` | 全没变，代价也没动 | 任务集没覆盖，先补任务 | **不编"略有提升"** |

`flat` 是最容易被产品经理讨厌、但最诚实的一种。第一次实跑就撞上了：
`pilots.rag_topk` 5 → 3，15 个任务 1.0 → 1.0，token 与步数都不动——
说明现有任务集里没有"依赖召回深度"的题。想测出这类收益，得先补题，而不是改结论的措辞。

`caveats` 是结论的一部分，不是附录。会把结论作废的前提必须跟着结论一起给：

- 走的是 mock 上游 → 只说明链路与策略生效，不能当模型能力结论；
- 每格只跑 1 次 → 任何通过率差异都和随机波动分不开；
- 有任务只差 1 次（列出 id）→ 样本内可能只是抖动；
- 任务数 < 10 → 宏平均容易被单个任务带偏；
- 两版证据覆盖都是 0 → 某些通道本来就不落 evidence，不是退步。

## 五、怎么用

### 5.1 命令行

```bash
# 跑一轮，跑完直接出结论行
python tools/bench.py --patch pilots.react_max_steps=8 --note "放宽步数上限"

# 只看某一轮的结论（base vs 候选）
python tools/bench.py --compare 7

# 跨轮比：第一版候选 vs 第二版候选
python tools/bench.py --compare 7,8
```

### 5.2 接口（admin 专属）

```
GET /api/bench/compare?a=<job>                    # 同一轮 base vs cand
GET /api/bench/compare?a=<jobA>&b=<jobB>          # 跨轮，默认都取 cand 阶段
GET /api/bench/compare?a=<job>&stage_a=base&stage_b=cand
GET /api/bench/detail?id=<job>                    # 详情里也带 verdict
POST /api/bench/run                               # 返回体里也带 verdict
```

返回结构（节选）：

```jsonc
{
  "a": {"job": 2, "stage": "base", "rev": 1, "sha": "3240caf7…", "ok_rate": 1.0},
  "b": {"job": 2, "stage": "cand", "rev": 3, "sha": "…", "ok_rate": 0.75},
  "verdict": {
    "tone": "worse",
    "headline": "先别上线：1 个任务稳定变坏（react-01），新的失败原因是「…」",
    "suggest": "先别上线",
    "lines": ["有效性：…", "代价基本没动…", "过程：被策略拒 1 个任务上升（0 → 1）"],
    "caveats": ["这轮走的是 mock 上游…"],
    "decisive": {"better": 0, "worse": 1, "unclear": 0, "same": 3}
  },
  "diff":     {"ok_rate": {"a": 1.0, "b": 0.75, "diff": -0.25, "dir": "down"}},
  "by_task":  [{"task_id": "react-01", "verdict": "worse", "ok_n_a": 3, "ok_n_b": 0,
                "new_fails": ["没有执行预期动作 search_docs（实际：无）"]}],
  "by_kind":  [{"kind": "react", "label": "ReAct", "tasks": 3, "worse": 1, "ok_a": 1.0, "ok_b": 0.667}],
  "scope":    {"common": ["react-01"], "only_a": ["rag-01"], "only_b": []},
  "note": "不给总分：只给同一批任务两次执行的差，以及一句能逐条复核的结论"
}
```

`by_kind` 回答的是"这轮改法在哪类任务上有效"——分工种看，比看总平均有用。

### 5.3 兼容性

`bench_run` 加了 `errors` / `dups` 两列，起服时自动 `ALTER TABLE` 补齐；
历史作业的行这两列为 NULL，比较时按 0 处理（不假装知道），因此旧作业的结论行里
"过程"一项会偏保守——少报，不假报。

## 六、验收

- 全套测试 **76 passed**（新增 `tests/test_compare.py` 11 例 + `test_bench.py` 补 3 处断言）。
  新用例全部用**构造的执行记录**，不真跑任务：这一层要验证的是"差异如何被归纳"，
  真跑会掺进模型与网络噪声，测到的就不是判据本身。
- 覆盖的六种结论各有一条用例，另有：单次执行不许判变坏、打转/出错在通过率不变的
  情况下也要被看见、跨轮对照、坏参数不崩。
- CI 冒烟 job 加了两步真实跑：
  1. 干净环境双跑 → 断言结论行存在、且每格 1 次时必须自己声明样本不足；
  2. 故意把检索预算清零 → 断言结论必须是 `worse` + "先别上线"，并点名 `react-01` 与 `search_docs`。
- 硬断言：`compare` 的输出里不允许出现 `score` / `grade` 这类字段（有个用例就是在查这个）。

## 七、已知边界（没做的和不该做的）

1. **没做统计显著性检验。** 15 个任务、每格 3 次，做 t 检验只是给噪声穿上白大褂。
   "差 ≥2 次才算数"这条经验规则更好解释，也更好推翻。任务数上到几百再谈检验。
2. **没做页面。** 结论行现在只能命令行或接口看到；「基准」页留给 P2-2。
3. **没做自动激活。** 结论只是建议，激活仍要走飞构的 `POST /api/harness/activate`，
   有人签字。这条是有意的：让"判定"和"决定"分开。
4. **mock 结论不算数。** 无 Key 环境跑出来的结果只证明链路通；任何关于模型能力的
   结论必须在真供应商上跑，结论行会自己说这句话。
